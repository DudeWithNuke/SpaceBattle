Задача: реализовать минимальное сетевое взаимодействие для пошаговой Unity-стратегии с host-authoritative архитектурой

Контекст проекта:
Игра — пошаговая онлайн-стратегия на 3D-сетке по типу «морского боя».
Игроки заранее размещают статичный флот на своей стороне поля.
Бой строится на применении способностей, разведке, скрытой информации, расчете попаданий, энергии, сигнатуры, сопротивления, точности и других характеристик.
Мультиплеер минимальный: 1 на 1, один игрок является Host, второй подключается как Client.
Host является авторитетным источником истины. Client не должен сам рассчитывать результат действий.

Главная цель:
Реализовать базовый сетевой слой, при котором:
1. Один игрок может создать матч как Host.
2. Второй игрок может подключиться как Client.
3. Оба игрока отправляют свои флоты Host-у.
4. Host валидирует флоты и запускает матч.
5. Игроки ходят по очереди.
6. Активный игрок отправляет Host-у намерение действия.
7. Host валидирует действие, рассчитывает результат и рассылает игрокам только разрешенное видимое состояние.
8. Матч завершается при выполнении условия победы.

Технологическое ограничение:
Использовать Unity.
Для сетевого слоя предпочтительно использовать Netcode for GameObjects или Mirror.
Реализация должна быть минимальной и понятной, без dedicated server, matchmaking, аккаунтов, рейтинга и сложного lobby-сервера.

Архитектурный принцип:
Не синхронизировать каждый объект сцены как NetworkObject без необходимости.
Синхронизировать в основном события, команды и изменения состояния.
Сетка и визуальные объекты могут существовать локально у каждого клиента.
Host хранит полное состояние боя.
Client получает только ViewModel/VisibleState, соответствующий информации, доступной конкретному игроку.

Этап 1. Подготовить сетевую инфраструктуру

Создать базовые классы:

- NetworkBootstrap
- NetworkMatchController
- PlayerConnectionInfo
- NetworkMessageModels

NetworkBootstrap должен уметь:
- запускать Host
- подключать Client по IP или локальному адресу
- отключаться от матча
- обрабатывать простые ошибки подключения

NetworkMatchController должен существовать на стороне Host и Client, но игровую логику выполнять только на Host.

Минимальные публичные методы:

- StartHost()
- StartClient(string address)
- Disconnect()
- SubmitFleetPreset(FleetPresetDto preset)
- RequestUseAbility(UseAbilityRequestDto request)
- RequestEndTurn()

Критерии готовности:
- Можно запустить две копии игры.
- Одна копия запускает Host.
- Вторая подключается как Client.
- В логах видно подключение двух игроков.
- Host может отличить Player1 и Player2.

Создать сериализуемые DTO-классы/структуры:

ShipPlacementDto:

- classId

CellCoordDto:

- z

UseAbilityRequestDto:

VisibleMatchStateDto:

ShipVisibleDto:

- DTO передают только данные.

Этап 3. Реализовать регистрацию игроков

При подключении игрока Host должен:
- назначить ему playerId
- сохранить подключение
- определить роль: HostPlayer или ClientPlayer
- уведомить всех игроков о количестве подключенных участников

Состояния матча:

MatchConnectionState:
- WaitingForPlayers
- WaitingForFleetPresets
- ReadyToStart
- InBattle
- Finished

Критерии готовности:
- Host получает playerId = 1.
- Client получает playerId = 2.
- Матч не стартует, пока нет двух игроков.
- При отключении одного игрока матч завершается или возвращается в безопасное состояние.

Этап 4. Реализовать отправку и валидацию флота

Client и Host отправляют FleetPresetDto на Host.

Host должен проверить:
- фракция существует
- корабли существуют
- размер флота не превышает лимит
- корабли не пересекаются
- корабли находятся внутри допустимой зоны игрока
- occupiedCells соответствуют размеру/форме корабля
- нет запрещенных классов/рангов
- у каждого корабля уникальный shipId

После успешной проверки Host сохраняет флот в FullMatchState.

Если флот невалиден:
Host отправляет ошибку конкретному игроку.

Если оба флота валидны:
Host переводит матч в ReadyToStart или сразу InBattle.

Критерии готовности:
- Оба игрока могут отправить флот.
- Host принимает валидные флоты.
- Host отклоняет невалидные флоты.
- Client не может навязать Host-у невозможное состояние.

Этап 5. Создать FullMatchState на Host

Создать чистую модель состояния боя, не завязанную на Unity-сцену:

FullMatchState:
- matchId
- players
- turnNumber
- currentPlayerId
- gridSize
- shipsById
- cellsState
- activeEffects
- battleLog
- randomSeed

ShipState:
- shipId
- ownerPlayerId
- shipTypeId
- factionId
- occupiedCells
- hp
- energy
- accuracy
- resistance
- signature
- bearing
- statuses
- abilities
- isDestroyed

CellState:
- coord
- occupyingShipId
- effects
- visibilityByPlayer

Важно:
FullMatchState должен существовать только на Host.
Client не должен получать полное состояние вражеского флота.

Критерии готовности:
- Host может создать FullMatchState после получения двух флотов.
- FullMatchState содержит оба флота.
- Client не имеет прямого доступа к FullMatchState.

Этап 6. Реализовать систему видимости

Создать VisibilityService.

Метод:

BuildVisibleStateForPlayer(
FullMatchState fullState,
int playerId
) -> VisibleMatchStateDto

Он должен вернуть:
- свои корабли полностью
- врага только в пределах обнаруженной информации
- известные клетки
- результаты сканирования
- публичные эффекты
- доступные действия текущего игрока

Запрещено:
- отправлять клиенту координаты всех кораблей врага
- отправлять полный HP врага, если он не должен быть известен
- отправлять скрытые статусы врага
- отправлять непубличные эффекты

Критерии готовности:
- Player1 и Player2 получают разные VisibleMatchStateDto.
- Каждый видит свой флот полностью.
- Вражеский флот скрыт, пока не обнаружен.
- После разведки открывается только разрешенная информация.

Этап 7. Реализовать пошаговый цикл

Создать TurnManager.

Логика:
- Host выбирает первого игрока.
- Host отправляет обоим игрокам TurnStarted.
- Только активный игрок может отправлять боевые действия.
- Неактивный игрок может только получать обновления.
- После действия можно либо завершить ход автоматически, либо ждать RequestEndTurn.
- Host переключает currentPlayerId.

Минимальные методы:

StartBattle()
StartTurn(int playerId)
EndCurrentTurn()
CanPlayerAct(int playerId)

Критерии готовности:
- Ход принадлежит только одному игроку.
- Неактивный игрок не может применять способности.
- После EndTurn ход переходит второму игроку.
- Номер хода увеличивается корректно.

Этап 8. Реализовать обработку действий

Создать ActionResolver.

Вход:
UseAbilityRequestDto

Алгоритм на Host:
1. Проверить, что матч в состоянии InBattle.
2. Проверить, что playerId является активным игроком.
3. Найти casterShipId.
4. Проверить, что корабль принадлежит игроку.
5. Проверить, что корабль не уничтожен.
6. Проверить, что abilityId существует у корабля.
7. Проверить энергию, cooldown, статусные ограничения.
8. Проверить допустимость targetCells.
9. Рассчитать результат.
10. Изменить FullMatchState.
11. Сформировать ActionResultDto.
12. Пересобрать VisibleMatchStateDto для каждого игрока.
13. Отправить каждому игроку его собственное видимое состояние.

Минимальный набор действий для MVP:
- AttackCell
- ScanArea
- EndTurn

AttackCell:
- игрок выбирает клетку
- Host проверяет возможность атаки
- Host рассчитывает попадание
- если в клетке есть корабль, наносит урон
- если HP <= 0, корабль уничтожается
- результат отправляется обоим игрокам с учетом видимости

ScanArea:
- игрок выбирает область
- Host рассчитывает обнаружение по сигнатуре/пеленгации
- обновляет visibilityByPlayer
- отправляет игроку результат разведки

Критерии готовности:
- Client отправляет только намерение.
- Host рассчитывает результат.
- Client не может сам назначить попадание.
- После действия оба игрока получают обновления.
- Скрытая информация не протекает.

Этап 9. Синхронизировать визуальное представление

Создать ClientBattleView.

Он принимает VisibleMatchStateDto и обновляет сцену:

- свои корабли
- видимые корабли врага
- маркеры известных клеток
- эффекты атак
- боевой лог
- UI текущего хода
- доступные кнопки действий

Важно:
ClientBattleView не должен рассчитывать боевую логику.
Он только отображает данные.

Критерии готовности:
- После старта матча игрок видит свой флот.
- Враг скрыт.
- После разведки появляются маркеры/обнаруженные цели.
- После атаки отображается результат.
- UI блокирует действия неактивного игрока.

Этап 10. Реализовать завершение матча

Host после каждого действия проверяет условие победы.

Минимальное условие:
- все корабли одного игрока уничтожены

Метод:

CheckVictory(FullMatchState state) -> MatchEndResultDto

MatchEndResultDto:
- winnerPlayerId
- loserPlayerId
- reason
- finalBattleLog

Критерии готовности:
- При уничтожении последнего корабля Host завершает матч.
- Оба игрока получают MatchEnded.
- UI показывает победу/поражение.
- После завершения нельзя отправлять действия.

Этап 11. Обработка ошибок и отказов

Реализовать базовые ошибки:

- NotYourTurn
- InvalidPlayer
- InvalidShip
- InvalidAbility
- NotEnoughEnergy
- InvalidTarget
- MatchNotStarted
- MatchAlreadyFinished
- FleetValidationFailed
- ConnectionLost

Client должен получать понятную ошибку и показывать ее в UI или лог.

Критерии готовности:
- Невалидные действия не ломают матч.
- Host не падает от неправильного DTO.
- Ошибки логируются.
- Игрок получает feedback.

Сделать тестовую сцену:

- кнопка Start Host

- кнопка Connect
- кнопка Submit Test Fleet
- кнопка Attack Cell

Тестовый флот:
- 2-3 корабля на игрока

- 1 сканирующая способность

Критерии готовности:
- Можно вручную запустить Host и Client.
- Оба отправляют тестовый флот.
- Матч стартует.
- Игроки ходят по очереди.
- Атака и сканирование работают.
- Победа определяется.

Этап 13. Минимальные автотесты игровой логики

Сделать unit-тесты не для сетевой библиотеки, а для чистой логики:

FleetValidatorTests:
- валидный флот проходит
- пересечение кораблей запрещено
- выход за границы запрещен

TurnManagerTests:
- активный игрок может ходить
- неактивный игрок не может ходить
- ход переключается

ActionResolverTests:
- атака по пустой клетке
- атака по кораблю
- уничтожение корабля
- запрет действия без энергии

VisibilityServiceTests:
- игрок видит свои корабли
- игрок не видит скрытого врага
- после скана информация появляется

Критерии готовности:
- Логика тестируется без запуска Unity-сцены.
- FullMatchState можно создавать в тестах.
- ActionResolver работает отдельно от визуала.

Финальный результат:
Должен получиться минимальный сетевой прототип, где два игрока могут сыграть простой матч 1 на 1:
- подключение Host/Client
- отправка флотов
- пошаговый цикл
- действия через Host
- скрытая информация
- обновление видимого состояния
- завершение матча

Главное архитектурное правило:
Client никогда не сообщает результат.
Client сообщает только намерение.
Host принимает решение, меняет состояние и рассылает видимые последствия.
